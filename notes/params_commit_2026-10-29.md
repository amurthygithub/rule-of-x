## 2. Readings chosen where round 2 is ambiguous or conflicts with the code (flagged)

1. **Engine success.a0 (Section 1.1).** The section says: recalibrate a0 so a reference process reaches production
   with probability about 0.50 *only if* the engine's b_bar carries the realization haircut, otherwise calibrate the
   product to 0.46. This commit sets success.b_bar = 0.67, so the first branch applies: a0 = 1.87 gives 0.50 at the
   reference (readiness 0.6, exposure 0.6, 50 affected FTE, average team and sponsor, log capability margin 0; the
   process factor expit(c0 - 0.4 - 0.4 ln 2) = 0.63 is unchanged). Consequence: the engine's expected realization at
   the reference is 0.50 x 0.67 = 0.34 before its own shock model, against Paper 1's 0.70 x 0.67 = 0.47. **Open:** the
   engine still applies its disruption shocks (plans.py flow survival and risk.py draws, the prop:ext-shocks
   implementation) on top of b_bar from an outcome survey, which is the double count Section 1.1 removes from P1.
   I kept the engine's shock model because the task keeps nu_D for the shock-timing results and the engine's success
   logit is calibrated to production attrition, not to an outcome survey; the engine builder should decide
   (engine/QA/ISSUES.md item 9).
2. **Compute-share cases.** Round 2 gives one value and range per horizon. Before, c_c had a "we use" range
   (0.15 to 0.25) and wider credible bounds (0.01 to 0.55). I used the code's own rule for class d composites
   (favorable and conservative = central halved and doubled: 2025 prices 0.03/0.06/0.12; 2028 0.06/0.12/0.24; 2031
   0.04/0.08/0.16; 2036 0.025/0.05/0.10) and the stated ranges as the credible bounds of the sensitivity
   (`cc_sensitivity`, now 0.01 to 0.30, the value-test cap). This matches the section's remark that the favorable 2028
   case gives a margin term of "about 0.76" (halving gives 0.757); taking the range ends instead would give 0.02 and a
   favorable margin term of about 0.83. One switch (`CC_CASES` in calibrate_horizons.py, line 110) changes it.
3. **The static ceiling (Table tab:ceiling) is at 2025 prices** (c_c 0.06, block `ceiling` of calibration_results.json);
   the horizon ceilings are in `ceiling_by_horizon`. The intercept path of Table tab:calib now moves toward the
   full-cost margin term at each horizon's compute share.
4. **Pass-through.** The task says to use dur = 1 - phi (1 - HHI). Paper 1 has no HHI, so calibrate_horizons.py uses
   the engine's competition.hhi = 0.25 (class d). The saving passed through is the non-fee unit cost of revenue the
   program removes, U0 - c_c(H), with U0 = 1 - median gross margin (0.740, core firms 2023-25, data/panel.csv) - fees
   0.025 = 0.235; the non-discretionary cost a is not passed through; the in-flight dip is a cost, not a saving, and is
   not passed through. Section 4's effect line ("the firm keeps half of the variable-cost saving") corresponds to
   HHI -> 0; at HHI 0.25 the firm keeps 0.625 (phi 0.5) and 0.475 (phi 0.7). In the engine the set enters through
   competition.phi_ind (the phi of dur), not finance.pass_through_phi, which stays the entrant scenario's extra
   pass-through; using the set in both would count pass-through twice. The engine's central case keeps the derived
   Cournot phi_ind (0.8 at HHI 0.25), above the set's top (engine/QA/ISSUES.md item 10).
5. **ICFR lines (Section 5.5).** The section targets $80k a year per in-scope AI application and lists the unit
   changes (c_chg 5k -> 2.5k, c_ops 30k -> 20k, c_ifc 15k -> 10k; setup and access kept). The listed changes do not
   reach the target: the upgrade retest accounting.C_val/T_up ($100k/1.22 = $82k a year) is in the line and is not
   among the listed lines. I applied the listed unit costs exactly (the section's operative values), recorded the
   $80k [$16k, $350k] (class b) as the reference total in params.yaml, and left C_val unchanged. Result: the accounting
   example's invoice application line is $266,967 (was $346,967) and the refund agent's $136,967 (was $156,967); the
   P1 line `\ItgcLine` is 0.027% of revenue (was 0.035%) and `\ItgcApps` 11 (was 9), not the "about thirty" the
   section derives. Reaching $80k needs C_val of about $24k (10 controls x 16 hours x $150, KPMG's test effort) or
   smaller example counts; that is the accounting theorist's call (open FT-20). The example counts (3 + 12 identities
   and permissions, 24 changes, operations $55k and $20k, 4 interfaces) and the prop:acct-amin example's own AI-layer
   line ($250k + $100k/1.0 = $350k, at the top of the new range) are example settings and were not changed.
6. **Effective rate.** The code's eff_rate (and `\PaceRateCen`) is q rho/clock, which excludes b_bar: 3.0% -> 6.3%. The
   auditor's "about 4.2%" includes b_bar; it is reported as `eff_rate_realized` (`\PaceRateRealCen` 4.2%).
7. **Slow case.** It takes the unfavorable end of every range (varpi 0.54, b_bar 0.37, T_emb 2, kappa 0.05). It now
   embeds 5.0% by 2036 (0.7% before), so the horizons sentence "under slow execution ... under 1%" no longer holds;
   paper1_macros.py's assertion was turned into a "TEXT CHECK" warning so the build continues.
8. **Revealed pace** is recorded only (class c, not a model input), as instructed; Section 1.5's option of adding it
   to the intercept path was not implemented.
9. **Not adopted (not Section 0 rows):** Section 2's remark that `inference_price.frontier_price_change_factor_per_year`

## 3. Cross-provider errors (Section 6)

checks, cross-model voting): none exists. What exists: within-provider common mode (`reliability.provider_correlation`,
risk.py: an event hits every process on the provider with probability rho), provider outages and diversity
(verify_part2_ext J1-J4, prop:ext-commonmode), and layered controls with a common-mode probability per control type
(engine formulas.amin_design, verify_part2_accounting 5a-5i; check 5c treats a layer on an independent model as
independent). So the new block is recorded in params_reliability.yaml and not wired; no engine key was added. No code
uses 0.60 as P(B wrong | A wrong) or as any conditional error probability (the 0.6 values found are reviewer catch
rates, monitor recall and unrelated example values). For the text owners: check 5c's independence is what Kim et al.
contradict in direction; the cross-provider joint-error rate stays class d.
